1. Padrões de Criação de Dados (Builders)

Criei dois padrões em __tests__/builders/: o UserMother, um Object Mother com umUsuarioPadrao() e umUsuarioPremium(), e o CarrinhoBuilder, um Data Builder. Escolhi o padrão de cada entidade pelo quanto ela varia entre os testes.

1.1 Por que CarrinhoBuilder e não CarrinhoMother

Um usuário só tem dois tipos relevantes para o checkout, PADRAO e PREMIUM. Dois métodos fixos cobrem todos os casos, e o UserMother continua pequeno.

O carrinho combina três eixos independentes: o usuário, a quantidade de itens e o preço de cada item. Um Object Mother precisaria de um método por combinação: umCarrinhoPremiumCom200Reais(), umCarrinhoPadraoVazio(), umCarrinhoPremiumComTresItens() e assim por diante. Cada cenário novo exigiria um método novo, e o nome esconderia os valores que o teste usa.

O CarrinhoBuilder parte de um carrinho válido (usuário padrão e 1 item de R$ 100) e oferece métodos fluentes que mudam só o necessário: comUser(user), comItens([...]), comItem(nome, preco) e vazio(). Cada um devolve this, o que permite encadear as chamadas. O build() devolve um Carrinho novo com uma cópia da lista de itens, para que um teste não altere o carrinho de outro.

1.2 Antes e depois

Antes: setup manual

const user = new User(
  2,
  'Cliente Premium',
  'premium@email.com',
  'PREMIUM'
);
const itens = [
  new Item('Teclado', 150),
  new Item('Mouse', 50),
];
const carrinho = new Carrinho(user, itens);

Depois: com UserMother e CarrinhoBuilder

const carrinho = new CarrinhoBuilder()
  .comUser(UserMother.umUsuarioPremium())
  .comItens([
    new Item('Teclado', 150),
    new Item('Mouse', 50),
  ])
  .build();

No "antes", o leitor precisa saber a ordem dos parâmetros de User para entender que 2 é o id e 'PREMIUM' é o tipo. O id e o nome não importam para o teste, mas aparecem com o mesmo peso que o tipo e os preços, que são o que importa. É o smell Obscure Setup.

1.3 Ganhos de legibilidade e manutenção

  • Legibilidade: o setup diz só o que o cenário exige, um cliente Premium e R$ 200 em itens. O resto vem dos valores padrão.
  • Manutenção: se o construtor de Carrinho ou de User mudar, a correção acontece no builder e no Mother, e não em cada teste. Isso evita o smell Fragile Test.
  • Independência: cada teste parte de um carrinho válido próprio e não depende de dados montados por outro teste.

2. Padrões de Test Doubles (Mocks vs. Stubs)

No teste de sucesso Premium, o GatewayPagamento e o PedidoRepository são stubs, e o EmailService é o mock.

// Arrange
const carrinho = new CarrinhoBuilder()
    .comUser(UserMother.umUsuarioPremium())
    .comItens([new Item('Teclado', 150), new Item('Mouse', 50)])
    .build();
gatewayStub = { cobrar: jest.fn().mockResolvedValue({ success: true }) };
repositoryStub = { salvar: jest.fn().mockImplementation(async (p) => ({ ...p, id: 42 })) };
emailMock = { enviarEmail: jest.fn().mockResolvedValue(undefined) };
const checkoutService = new CheckoutService(gatewayStub, repositoryStub, emailMock);

// Act
pedido = await checkoutService.processarPedido(carrinho, CARTAO);

// Assert
expect(gatewayStub.cobrar).toHaveBeenCalledWith(180, CARTAO);
expect(emailMock.enviarEmail).toHaveBeenCalledTimes(1);
expect(emailMock.enviarEmail).toHaveBeenCalledWith(
    'premium@email.com', 'Seu Pedido foi Aprovado!', 'Pedido 42 no valor de R$180');

No arquivo, o Arrange e o Act ficam num beforeEach, e cada it verifica uma coisa: o valor cobrado, o e-mail enviado e o pedido retornado.

DependênciaPapelO que o teste faz com elaVerificação
GatewayPagamentoStub (principalmente)Responde { success: true } para o fluxo seguir; o valor cobrado também é conferidoEstado (principal) e comportamento (argumento 180)
PedidoRepositoryStubDevolve o pedido com id: 42Estado (pedido retornado)
EmailServiceMockRegistra a chamada para o teste conferir quantas vezes e com quais argumentosComportamento

2.1 Por que o GatewayPagamento é (principalmente) um Stub

O gateway está no teste para controlar o fluxo. O CheckoutService só cria o pedido se cobrar() devolver success: true, então o stub fornece essa resposta pré-definida sem chamar um gateway real. O resultado depende dessa resposta, e não de como o gateway foi usado: é a verificação de estado descrita por Fowler em Mocks Aren't Stubs.

É "principalmente" stub porque o teste também confere que cobrar recebeu 180. O totalFinal do pedido retornado mostra o valor calculado, mas só o argumento enviado ao gateway prova que o cliente foi cobrado com o desconto. Meszaros chama esse uso de Test Spy: um stub que também registra as chamadas recebidas. Mesmo assim, a função principal do gateway no teste é responder.

2.2 Por que o EmailService é um Mock

O e-mail é um efeito colateral. O processarPedido não devolve nada sobre ele, e o checkout continua mesmo se o envio falhar. Não há estado para conferir, então a única forma de saber se o cliente foi avisado é verificar a interação: enviarEmail foi chamado 1 vez, para premium@email.com, com o assunto "Seu Pedido foi Aprovado!" e o corpo com o id e o valor do pedido. É a verificação de comportamento. No Jest, esse "mock" é um jest.fn() conferido depois da execução; na taxonomia de Meszaros isso também é um Test Spy, mas no sentido de Fowler é o double usado para verificar comportamento.

2.3 Dummies no teste de falha

No teste de falha no pagamento, o repositório e o serviço de e-mail são objetos vazios ({}). Eles só preenchem o construtor do CheckoutService. Eles deixam claro que nenhum dos dois deve ser usado quando o pagamento falha. Se o código chamasse o repositório por engano, o teste quebraria com TypeError. O e-mail é um caso diferente: a chamada fica dentro de um try/catch no CheckoutService, então o erro seria só registrado no console. A asserção é só de estado: expect(pedido).toBeNull().

Além dos dois cenários pedidos, adicionei dois testes: o cliente padrão é cobrado em R$ 200, sem desconto, e o checkout é concluído mesmo quando o envio de e-mail falha (mockRejectedValue). A suíte ficou com 6 testes, todos passando com npm test.

Observação de ambiente: o projeto base declara babel-jest, mas não trazia configuração do Babel, e o Jest falhava nos import. Adicionei babel.config.cjs com @babel/preset-env e configurei o Jest para não tratar __tests__/builders/ como suíte de teste.

3. Conclusão

No trabalho anterior, os test smells foram corrigidos depois de aparecerem. Aqui, os padrões foram escolhidos antes do primeiro teste, e os smells não chegaram a surgir.

  • Builders contra Obscure Setup: o UserMother e o CarrinhoBuilder deixam no teste só os dados que definem o cenário, e uma mudança nas classes de domínio é corrigida num lugar só.
  • Test doubles contra Fragile Test: nenhum teste depende de gateway, banco ou servidor de e-mail reais. A suíte roda em cerca de 1 segundo e falha por causa da regra de negócio, não da infraestrutura.
  • Stub ou mock por escolha: usar stub para controlar respostas e mock só onde a interação é o resultado evita testes que conferem cada chamada interna e quebram a cada refatoração.

Com esses padrões e a estrutura Arrange, Act, Assert, a suíte é rápida de ler, barata de manter e fácil de estender para novos cenários.

Referências: Jest, Mock Functions (jestjs.io/docs/mock-functions); Martin Fowler, Mocks Aren't Stubs (martinfowler.com/articles/mocksArentStubs.html); Gerard Meszaros, xUnit Test Patterns (xunitpatterns.com).
